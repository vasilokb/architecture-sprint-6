## Описание задачи
Сервис `client-info` сталкивается с проблемой высокой вариативности запросов от потребителей (`insuretech_web` и `core-app`) в сценариях продажи и обслуживания страховок. Карточка клиента включает 500 атрибутов, но потребители запрашивают разные комбинации данных (например, контакты, документы, родственники). Текущий REST API предоставляет отдельные ресурсы для каждого типа данных, что приводит к множественным запросам и увеличению RPS (Requests Per Second). Предоставить единый ресурс для всех данных невозможно из-за большого объёма данных, который замедлит взаимодействие, особенно с веб-приложением. Команда решила перевести REST API `client-info` на GraphQL.

### Цели
1. Снизить количество запросов, устраняя дублирование вызовов.
2. Обеспечить гибкость в выборе запрашиваемых данных.
3. Оптимизировать взаимодействие между потребителями и `client-info`.

## Анализ Swagger-контракта сервиса `client-info`

### 1. Общая структура API
- **Название сервиса**: Клиентский Сервис (`client-info`).
- **Версия**: 1.0.0.
- **Базовый путь**: `/v1`.
- **Протокол**: HTTPS.
- **Хост**: `api.client-service.com`.
- **Формат данных**: JSON (`application/json`).
- **Описание**: API предоставляет доступ к данным клиентов, включая их основные атрибуты, документы и родственников.

### 2. Ключевые ресурсы
- **Client (Клиент)**:
    - Атрибуты:
        - `id`: Идентификатор клиента (string).
        - `name`: Имя клиента (string).
        - `age`: Возраст клиента (integer).
- **Document (Документ)**:
    - Атрибуты:
        - `id`: Идентификатор документа (string).
        - `type`: Тип документа (string, например, "passport").
        - `number`: Номер документа (string).
        - `issueDate`: Дата выдачи (string).
        - `expiryDate`: Дата истечения (string).
- **Relative (Родственник)**:
    - Атрибуты:
        - `id`: Идентификатор родственника (string).
        - `relationType`: Тип родства (string, например, "spouse").
        - `name`: Имя родственника (string).
        - `age`: Возраст родственника (integer).

### 3. Ключевые операции (эндпоинты)
- **`GET /clients/{id}`**:
    - **Тег**: Клиент.
    - **Описание**: Получение основной информации о клиенте по его ID.
    - **Параметры**: `id` (path, required, string) — идентификатор клиента.
    - **Ответ**: Объект `Client` (id, name, age).
    - **Пример запроса**: `GET /v1/clients/client-123`.
    - **Пример ответа**:
      ```json
      {
        "id": "client-123",
        "name": "John Doe",
        "age": 35
      }
      ```

- **`GET /clients/{id}/documents`**:
    - **Тег**: Документы.
    - **Описание**: Получение списка документов клиента.
    - **Параметры**: `id` (path, required, string) — идентификатор клиента.
    - **Ответ**: Массив объектов `Document` (id, type, number, issueDate, expiryDate).
    - **Пример запроса**: `GET /v1/clients/client-123/documents`.
    - **Пример ответа**:
      ```json
      [
        {
          "id": "doc-1",
          "type": "passport",
          "number": "123456789",
          "issueDate": "2020-01-01",
          "expiryDate": "2030-01-01"
        },
        {
          "id": "doc-2",
          "type": "driver_license",
          "number": "987654321",
          "issueDate": "2021-01-01",
          "expiryDate": "2031-01-01"
        }
      ]
      ```

- **`GET /clients/{id}/relatives`**:
    - **Тег**: Родственники.
    - **Описание**: Получение списка родственников клиента.
    - **Параметры**: `id` (path, required, string) — идентификатор клиента.
    - **Ответ**: Массив объектов `Relative` (id, relationType, name, age).
    - **Пример запроса**: `GET /v1/clients/client-123/relatives`.
    - **Пример ответа**:
      ```json
      [
        {
          "id": "rel-1",
          "relationType": "spouse",
          "name": "Jane Doe",
          "age": 32
        },
        {
          "id": "rel-2",
          "relationType": "child",
          "name": "Mike Doe",
          "age": 10
        }
      ]
      ```

### 4. Оценка текущей структуры API
- **Проблемы**:
    1. **Множество запросов**: Для получения данных клиента, его документов и родственников требуется 3 отдельных запроса, что увеличивает RPS и нагрузку на сервис, особенно при вариативных сценариях (продажа, обслуживание).
    2. **Вариативность данных**: Разные сценарии требуют разных комбинаций данных из 500 атрибутов, но REST возвращает фиксированные наборы, что приводит к передаче ненужных данных.
    3. **Объём данных**: Передача полного объекта клиента (500 атрибутов) замедляет взаимодействие, особенно с веб-приложением, а текущие эндпоинты ограничены.
    4. **Отсутствие связности**: Нельзя получить связанные данные (клиента, документы, родственников) в одном запросе, что увеличивает задержки.
- **Преимущества**:
    - Простота: REST API интуитивно понятен.
    - Разделение ресурсов: Каждый эндпоинт отвечает за конкретный тип данных.
- **Вывод**: REST API неэффективен для вариативных запросов, увеличивает нагрузку и не позволяет гибко запрашивать данные.

## Проектирование GraphQL API

### 1. Сущности и их поля
- **Client (Клиент)**:
    - **Поля**:
        - `id: String!` — идентификатор клиента (обязательное поле).
        - `name: String` — имя клиента.
        - `age: Int` — возраст клиента.
        - `documents: [Document]` — список документов клиента.
        - `relatives: [Relative]` — список родственников клиента.
    - **Обоснование**: Поля `id`, `name`, `age` соответствуют Swagger. Добавлены связи `documents` и `relatives`, чтобы покрыть операции `GET /clients/{id}/documents` и `GET /clients/{id}/relatives` в одном запросе.

- **Document (Документ)**:
    - **Поля**:
        - `id: String!` — идентификатор документа.
        - `type: String` — тип документа.
        - `number: String` — номер документа.
        - `issueDate: String` — дата выдачи.
        - `expiryDate: String` — дата истечения.
    - **Обоснование**: Полностью отражает структуру из Swagger.

- **Relative (Родственник)**:
    - **Поля**:
        - `id: String!` — идентификатор родственника.
        - `relationType: String` — тип родства.
        - `name: String` — имя родственника.
        - `age: Int` — возраст родственника.
    - **Обоснование**: Полностью отражает структуру из Swagger.

### 2. Необходимые запросы (Queries)
- **Query: getClient**:
    - **Описание**: Запрос для получения данных клиента по его `id` с возможностью выбора связанных данных.
    - **Параметры**:
        - `id: String!` — идентификатор клиента.
    - **Возвращаемый тип**: `Client`.
    - **GraphQL-определение**:
      ```graphql
      type Query {
        getClient(id: String!): Client
      }
      ```
    - **Обоснование**: Покрывает все REST-операции (`GET /clients/{id}`, `/clients/{id}/documents`, `/clients/{id}/relatives`) одним запросом, устраняя дублирование вызовов.

### 3. Полная GraphQL-схема
```graphql
type Client {
  id: String!
  name: String
  age: Int
  documents: [Document]
  relatives: [Relative]
}

type Document {
  id: String!
  type: String
  number: String
  issueDate: String
  expiryDate: String
}

type Relative {
  id: String!
  relationType: String
  name: String
  age: Int
}

type Query {
  getClient(id: String!): Client
}
```

### 4. Оптимизация взаимодействия с помощью GraphQL

#### Проблемы REST API
- **Множество запросов**: Для получения данных клиента, его документов и родственников требуется 3 отдельных запроса, что увеличивает RPS и нагрузку.
- **Вариативность данных**: REST возвращает фиксированные наборы, передавая ненужные данные.
- **Объём данных**: Передача полного объекта клиента (500 атрибутов) замедляет взаимодействие.
- **Отсутствие связности**: Нельзя получить связанные данные в одном запросе.

#### Как GraphQL решает проблемы
- **Снижение количества запросов**:
    - Один запрос `getClient(id)` заменяет 3 REST-вызова, снижая RPS (с 3 до 1 на сценарий). Это уменьшает нагрузку на `client-info`.
    - **Пример**: Вместо трёх вызовов клиент выполняет `getClient(id) { name, documents { number }, relatives { name } }`.

- **Гибкость в выборе данных**:
    - Клиент запрашивает только нужные поля (например, `name`, `age`, или `documents { number }`), минимизируя объём данных. Это ускоряет взаимодействие, особенно для веб-приложения.
    - **Пример**: Запрос `getClient(id) { name }` возвращает только имя, а не 500 атрибутов.

- **Поддержка сложных сценариев**:
    - Вложенные поля (`documents`, `relatives`) позволяют получить связанные данные в одном запросе, устраняя дублирование.
    - **Пример**: `getClient(id) { name, documents { number }, relatives { name } }` объединяет данные клиента, документов и родственников.

- **Оптимизация производительности**:
    - GraphQL фильтрует данные на сервере, возвращая только запрошенное, что снижает нагрузку на сеть и сервер.
    - **Пример**: Вместо 500 атрибутов возвращаются только 5 запрошенных полей.

- **Устойчивость к изменениям**:
    - Добавление новых полей (например, `email` в `Client`) не ломает существующие запросы, упрощая эволюцию сервиса.

#### Ограничения и рекомендации
- **Ограничения**: GraphQL требует сложной реализации (резолверы для вложенных полей) и защиты от сложных запросов (Depth Limiting).
- **Рекомендации**: Добавить Rate Limiting и мониторинг производительности GraphQL-запросов.
